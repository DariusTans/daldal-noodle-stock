## ข้อมูลตัวอย่างพร้อมใช้ (v0.8.1)

เปิดลิงก์ปกติจะเข้าชุดข้อมูลตัวอย่างทันที มีทะเบียน 8 รายการ หน่วย 6 หน่วย ยอดนับยืนยัน 7 รายการ เกณฑ์เตือน 7 รายการ เสนอซื้อ 6 รายการ ใบซื้อ 4 ใบ ตรวจรับ 2 ครั้ง และบิล 5 ใบ พร้อมภาพหลักฐานและรายงาน ข้อมูลทั้งหมดสมมติ แก้ไขทดลองได้และบันทึกไว้เมื่อเปิดครั้งถัดไป ไม่สร้างซ้ำทุกครั้งที่เข้า

กด “ข้อมูลของฉัน” เพื่อกลับข้อมูลเดิม (`?data=workspace#home`) ชุดตัวอย่างใช้พื้นที่แยก ไม่ล้างหรือรวมกับข้อมูลเดิม บทบาทและเกณฑ์ผู้พิจารณาทั้งหมดเป็นตัวอย่าง ชื่อผู้ตรวจ: เจ้าของตัวอย่าง

Dashboard ของชุดตัวอย่างเริ่มแสดงทุกช่วงวันที่เพื่อไม่ให้ข้อมูลหายจากมุมมองเมื่อเปลี่ยนเดือน ไฟล์สำรองและ CSV ของชุดตัวอย่างมีคำว่า demo ในชื่อ

## เปิดใช้งาน

เปิด `index.html` ด้วย Chrome หรือใช้ลิงก์หลักจาก `เปิดระบบ.url` เมื่อเผยแพร่สำเร็จ ข้อมูลของไฟล์ในเครื่องและลิงก์เว็บไซต์แยกกัน ย้ายข้อมูลด้วยการสำรอง/นำเข้า JSON

## รอบที่ 1

- ทะเบียนวัตถุดิบ: ค้นหา กรองหมวด/สถานะ เพิ่ม แก้ไข พัก/เปิดใช้งาน และดูรายละเอียด/ประวัติ
- หน่วยนับ: เพิ่ม/แก้ไข ตรวจชื่อและหน่วยย่อซ้ำ ป้องกันเปลี่ยนประเภทของหน่วยที่ถูกใช้
- บทบาทจำลอง: หุ้นส่วน/เจ้าของ ผู้จัดการ และพนักงาน
- ข้อมูลอยู่ในเบราว์เซอร์ บันทึกข้ามการรีเฟรช สำรอง/นำเข้า JSON ได้
- ตรวจข้อมูลเปลี่ยนจากอีกหน้าต่าง ป้องกันเขียนทับข้อมูลที่อ่านไม่ได้

## รอบที่ 2 — นับและยืนยันสต็อก

1. เลือก “นับและยืนยันสต็อก” แล้วเปิดรอบ ระบุชื่อรอบและผู้เริ่มนับ
2. กรอกจำนวนจริง ช่องว่าง = ยังไม่ได้นับ; 0 = นับแล้วไม่มีของ บันทึกร่างและกลับมาทำต่อได้
3. เมื่อแก้ยอดที่เคยบันทึก ต้องระบุเหตุผล และเมื่อยอดต่างจากรอบยืนยันก่อน ต้องอธิบายก่อนส่งตรวจ
4. กดบันทึกและส่งตรวจ หุ้นส่วนหรือผู้จัดการในบทบาทจำลองสามารถส่งกลับพร้อมเหตุผล หรือตรวจและยืนยันยอด
5. รอบที่ยืนยันแล้วล็อกแก้ย้อนหลังไม่ได้ ดูยอดได้ที่ “ยอดนับล่าสุด” พร้อมผู้ทำรายการ เวลา และรอบอ้างอิง

เปิดได้ครั้งละหนึ่งรอบ ประวัติเก็บชื่อและหน่วย ณ วันเปิดรอบ การแก้ทะเบียนภายหลังไม่เปลี่ยนประวัติ หน่วยของวัตถุดิบที่มีรอบนับแล้วเปลี่ยนไม่ได้ ต้องสร้างรายการใหม่ ยอดต่างจากการนับครั้งก่อนไม่ใช่ยอดใช้หรือของเสีย และยอดล่าสุดไม่ใช่คงเหลือเรียลไทม์

ข้อมูลเดิม schema 1–5 อัปเกรดเป็น schema 6 อัตโนมัติ โดยสำรองต้นฉบับที่ key `daldal-operations-data-before-v6` และรักษารหัสกับประวัติเดิม นำเข้า JSON ได้รุ่น 1–6 การนำเข้าเป็นการแทนที่ข้อมูล ไม่ใช่รวมข้อมูล ควรสำรองก่อน

## รอบที่ 3 — เคลื่อนไหวสต็อกและเตือนซื้อ

1. ต้องมียอดนับยืนยันตั้งต้นก่อน เปิด “เคลื่อนไหวสต็อก” เพื่อรับเข้า เบิกใช้ หรือบันทึกของเสีย ระบุจำนวน ผู้ทำรายการ เหตุผล และเลขอ้างอิงถ้ามี
2. หุ้นส่วน/ผู้จัดการจำลองปรับเพิ่ม ลด หรือกลับรายการผิดได้ ระบบเก็บต้นฉบับพร้อมรายการหักล้าง ไม่ลบประวัติ และไม่ให้ยอดคำนวณติดลบ
3. ยอดคำนวณ = ยอดนับยืนยันล่าสุด + รายการเคลื่อนไหวหลังรอบนั้น ถ้าข้อมูลยังไม่ครบ ระบบคงใช้ยอดนับล่าสุดเป็นยอดอ้างอิงเตือนซื้อ
4. ผู้ตรวจเปิด “ตรวจความครบ” ระบุขอบเขต/หลักฐานและรับรองว่าลงรับเข้า เบิกใช้ ของเสีย ปรับยอดครบถึงเวลานี้ จึงใช้ยอดคำนวณได้ เมื่อมีรายการใหม่ต้องตรวจอีกครั้ง
5. เปิด “เตือนซื้อ / เสนอซื้อ” ตั้งจุดเตือนและยอดเป้าหมายต่อวัตถุดิบ ไม่มีค่าเกณฑ์ที่สมมติให้ร้าน เตือนเมื่อยอดอ้างอิง **น้อยกว่าหรือเท่ากับ** จุดเตือน เป้าหมายต้องมากกว่าจุดเตือน
6. จำนวนเสนอ = เป้าหมาย − ยอดอ้างอิง กดร่างเสนอซื้อ คนตรวจสามารถเปลี่ยนจำนวนพร้อมเหตุผล แล้วยืนยันเป็น “ตรวจแล้ว รอจัดซื้อ” มีร่าง/รายการค้างได้หนึ่งรายการต่อวัตถุดิบ
7. หากยอด ข้อมูลความครบ หรือเกณฑ์เปลี่ยน ให้ “อัปเดตร่าง” ก่อนยืนยัน ถ้าไม่เข้าเกณฑ์แล้วให้ยกเลิก ร่างที่ตรวจแล้วเปลี่ยนไม่ได้ ให้ยกเลิกพร้อมเหตุผลแล้วสร้างใหม่

### ขอบเขตการใช้งานรอบนี้

- รับ/เบิก/ของเสียเป็นการบันทึกด้วยมือ ไม่เชื่อมยอดขาย การรับจากใบซื้อเชื่อมผ่านหน้าตรวจรับในรอบ 5
- ลงรายการ ณ เวลาบันทึก ไม่ลงย้อนหลัง ห้ามลงซ้ำของที่นับรวมไปแล้ว หากผิดก่อนรอบนับล่าสุด ใช้ตรวจนับใหม่หรือปรับยอดปัจจุบันพร้อมเหตุผล
- ตอนเปิดรอบนับ ระบบพักการเคลื่อนไหวและเสนอซื้อจนจบรอบ ควรหยุดรับ/เบิกจริงระหว่างนับและตรวจยืนยัน เพื่อให้ยอดต่อกันได้
- รอบนับใหม่เก็บยอดคาดหมายเฉพาะวัตถุดิบที่ตรวจเคลื่อนไหวครบตอนเปิดรอบ และให้ระบุเหตุผลเมื่อยอดจริงต่าง หลังยืนยันจะเริ่มฐานใหม่ ไม่บวกรายการก่อนรอบซ้ำ
- การตรวจครบเป็นคำรับรองของคนตามเวลาที่ระบุ ไม่ได้พิสูจน์ว่าร้านบันทึกทุกเหตุการณ์จริง และไม่ใช่ยอดเรียลไทม์
- แจ้งเตือนเฉพาะในระบบ ไม่มี LINE ไม่มีราคาสด ไม่มีการสั่งซื้อหรืออนุมัติเงิน ขั้น “ตรวจแล้ว รอจัดซื้อ” เปิดทำต่อได้ในเมนูจัดซื้อและอนุมัติ
- บทบาทพนักงานบันทึกรับ/เบิก/ของเสียและสร้างร่างซื้อได้ หุ้นส่วน/ผู้จัดการตรวจความครบ ตั้งเกณฑ์ ปรับยอด กลับรายการ และตรวจ/ยกเลิกเสนอซื้อได้ เป็นข้อเสนอให้ร้านทบทวนก่อนใช้จริง

## รอบที่ 4 — จัดซื้อและอนุมัติ

1. ทดลองบทบาทหุ้นส่วนหรือผู้จัดการ เปิด “จัดซื้อและอนุมัติ” แล้วเลือกจากรายการเสนอซื้อที่ตรวจแล้ว หนึ่งรายการต่อหนึ่งใบ เลือกสกุลเงินชัดเจน
2. เพิ่มทางเลือกซื้อ: ร้าน ขนาดบรรจุในหน่วยนับเดิม ราคาต่อชุดซื้อรวมภาษี ค่าส่ง ค่าใช้จ่ายเพิ่ม ส่วนลดทั้งใบ ที่มา/เวลาตรวจราคา และเงื่อนไข
3. ระบบคำนวณจำนวนชุดซื้อโดยปัดขึ้นให้พอจำนวนที่ต้องการ รวมเงิน และต้นทุนต่อหน่วยนับ คนเป็นผู้เลือกพร้อมเหตุผล รองรับแหล่งเดียวได้โดยอธิบายเหตุผล ไม่สมมติราคาสด
4. เจ้าของตั้ง “เกณฑ์อนุมัติทดลอง”: สกุลเงิน ชื่อ/บทบาทผู้พิจารณา ทุกใบหรือเฉพาะยอดเกินวงเงินต่อใบ และที่มาของเกณฑ์ ไม่มีค่า 5,000 หรือชื่อผู้อนุมัติเดาให้
5. ส่งพิจารณา ผู้พิจารณาต้องตรงชื่อและบทบาทที่ตั้งไว้ เลือกผ่าน ส่งกลับพร้อมเหตุผล หรือไม่อนุมัติ แม้ยอดไม่เกินวงเงินยังต้องให้คนรับรองก่อนซื้อ
6. ถ้าราคา จำนวน หรือแหล่งซื้อเปลี่ยนหลังส่ง/อนุมัติ ให้ถอนกลับแก้ไขแล้วส่งพิจารณาใหม่ เก็บประวัติเดิม ถ้าสต็อกหรือเกณฑ์เปลี่ยน ระบบจะกันการผ่านขั้นถัดไปจนทบทวน
7. เมื่อซื้อภายนอกจริงตามที่ผ่านพิจารณาแล้ว จึง “บันทึกว่าซื้อแล้ว” พร้อมเลขอ้างอิง สถานะเป็น “ซื้อแล้ว รอตรวจรับ” ยังไม่เพิ่มสต็อกหรือยืนยันค่าใช้จ่าย

### ขอบเขตและเกณฑ์ทดลอง

- ชุดซื้อ = บรรจุที่ผู้ขายขายหนึ่งชุด เช่น 1 ลังมี 3 แพ็ก ถ้าต้องการ 10 แพ็ก จะเสนอซื้อ 4 ชุด = 12 แพ็ก ต้องตรวจจำนวนเกินจากการปัดบรรจุด้วยคน
- เทียบภายในสกุลเงินเดียว ไม่แปลงเงิน ไม่รวมค่าส่ง/ส่วนลดข้ามใบ และไม่รวมยอดต่อวันหรือผู้ขาย เกณฑ์ “เกิน” ใช้ >; ยอดเท่ากับวงเงินถือว่าไม่เกิน
- ไม่มีการจ่ายเงินหรือส่งคำสั่งซื้อให้ร้านค้า ปุ่มซื้อแล้วเป็นบันทึกสิ่งที่ทำภายนอก ต้องรักษาใบอ้างอิงจริง
- พนักงานจำลองยังไม่เห็นราคา/งานจัดซื้อ ผู้จัดการและหุ้นส่วนทำงานซื้อได้ เจ้าของตั้งเกณฑ์ ผู้พิจารณาเป็นชื่อ/บทบาทตามค่าทดลอง ทั้งหมดไม่ใช่ระบบพิสูจน์ตัวตน
- ผู้อนุมัติจริง เกณฑ์วงเงินที่นับต่ออะไร/สกุลเงิน และขั้นตอนเร่งด่วนยังต้องตกลงก่อนใช้จริง ต้นแบบไม่มีช่องทางข้ามอนุมัติกรณีเร่งด่วน
- ยังไม่รองรับแบ่งซื้อหลายผู้ขายในรายการเดียว การรับบางส่วนและติดตามปัญหาใช้หน้าตรวจรับ รอบ 5


## รอบที่ 5 — ตรวจรับสินค้า (v0.5.0)

- เปิดเมนูตรวจรับจากใบซื้อเดิม จำนวนคาดรับใช้จำนวนสั่งจริงหลังปัดบรรจุ
- พนักงานร่างผลตรวจ จำนวนผ่านตรวจ/ไม่รับ เลขส่งของ ผู้ตรวจ และหมายเหตุ โดยไม่แสดงราคา
- ผู้จัดการหรือเจ้าของรับรองผลตรวจและยืนยันว่ายังไม่รวมของนี้ในยอดนับก่อนยืนยันลงสต็อกครั้งเดียว
- รองรับรับบางส่วน ของเสียหาย/ผิดรายการ ติดตามผล และส่งทดแทนด้วยใบรับใหม่
- ยกเลิกร่างหรือกลับยอดใบรับพร้อมประวัติได้ก่อนปิดรับ การกลับยอดต้องยังอยู่ในฐานนับเดิมและยอดคงเหลือพอ
- ปิดรับครบหรือปิดบางส่วนพร้อมเหตุผลและรับรองไม่รับส่วนที่เหลือ ต้องเคลียร์ร่างและปัญหาค้างก่อน เมื่อปิดแล้วรายการเสนอซื้อเสร็จสิ้น เปิดเสนอรอบใหม่ได้
- ปิดรับไม่คืนเงินหรือรับรองค่าใช้จ่าย การยืนยันรับไม่เท่ากับรับรองว่ารายการเคลื่อนไหวทั้งหมดครบ
- เก็บ storage key เดิม อัปเกรด schema 1–4 เป็น 5 พร้อมสำรองต้นฉบับ before-v6; ไม่ seed ทับข้อมูลเดิม

ข้อจำกัด: ยังคงเป็นต้นแบบเก็บข้อมูลในเบราว์เซอร์ บทบาทจำลอง ไม่มีบัญชีจริงหรือฐานข้อมูลส่วนกลาง ไม่รับเกินใบซื้อ ไม่เปิดแก้ใบที่ปิดรับแล้ว หากยอดรวมอยู่ในการนับไปแล้วห้ามรับซ้ำ

## ข้อจำกัดและข้อมูลทดลอง

วัตถุดิบตั้งต้นเป็นข้อมูลสมมติ ไม่มีข้อมูลยอดขาย ยอดนับต้องบันทึกจากของจริง ไม่มีฐานข้อมูลส่วนกลาง บัญชีผู้ใช้จริง หรือ AI/OCR จริง ทุกคนที่เข้าถึงต้นแบบสลับบทบาทได้ จึงไม่ใช่การควบคุมสิทธิ์ที่ปลอดภัย สิทธิ์ผู้จัดการเป็นข้อเสนอรอยืนยันกับ P’J

การแก้ชื่อหน่วยมีผลต่อชื่อที่แสดงในทะเบียนที่อ้างอิง ยังไม่รองรับแปลงหน่วยซื้อ/หน่วยใช้ ไม่ลบหน่วยหรือวัตถุดิบเพื่อรักษาการอ้างอิง ใช้พักวัตถุดิบแทน

หากเบราว์เซอร์บันทึกไม่ได้ตั้งแต่เริ่ม ระบบเตือนและใช้ข้อมูลเฉพาะรอบนั้น หากพื้นที่เต็มระหว่างบันทึก จะปฏิเสธรายการใหม่และรักษาชุดเดิม หากข้อมูลเดิมเสียหาย จะเปิดข้อมูลตัวอย่างแบบอ่านอย่างเดียวและให้ดาวน์โหลดข้อมูลเสียหายเพื่อกู้คืน

## วิธีต่อยอด

ใช้โฟลเดอร์ Product นี้เป็นโปรเจกต์หลัก อัปเดต Site ID เดิมใน `.openai/hosting.json` ไม่สร้าง Site ใหม่

1. แก้ `index.html` และ `assets/` ซึ่งเป็น source หลัก
2. คง storage key `daldal-operations-data` และรหัสวัตถุดิบ/หน่วยเดิม
3. เพิ่ม migration พร้อมสำรองก่อนเปลี่ยน schemaVersion ห้าม seed ทับข้อมูลผู้ใช้
4. รันทดสอบใน `tests/` และ browser QA
5. คัดลอก source เว็บลง `dist/` โดยไม่ใส่เอกสารหรือข้อมูลผู้ใช้
6. ใช้ Sites source workflow เพื่อ commit/push/package และ deploy private Site เดิม
7. อัปเดต CHANGELOG และ HANDOFF โดยคงลิงก์หลัก

## ลำดับถัดไป

ทบทวนต้นแบบครบ 7 รอบ แล้วตกลงการเชื่อม AI/OCR บัญชีผู้ใช้จริง และฐานข้อมูลส่วนกลาง

ทำทีละส่วนและให้ผู้ใช้ทบทวนก่อนทำรอบถัดไป เกณฑ์อนุมัติซื้อ การใช้วัตถุดิบ ผู้ตรวจบิล และรูปแบบรายงานยังต้องยืนยัน

## รอบที่ 6 — บิลและค่าใช้จ่าย (v0.6.0, 29 ตุลาคม 2026)

1. เจ้าของตั้งชื่อและบทบาทผู้ตรวจทดลองก่อนส่งตรวจ ไม่สมมติผู้ตรวจให้ร้าน
2. ผู้จัดการ/เจ้าของสร้างร่าง: ร้านค้า วันที่ เลขบิล ยอดรวม สกุลเงิน หมวด เงินร้าน/สำรองส่วนตัว ชื่อผู้จ่าย และรายละเอียด เชื่อมใบซื้อเดิมได้โดยไม่เพิ่มสต็อก
3. แนบหลักฐาน PNG/JPEG/WebP/PDF หนึ่งไฟล์ต่อรายการ ไม่เกิน 350 KB รวมไม่เกิน 1.4 MB เพื่อใช้กับพื้นที่เบราว์เซอร์ หากไม่มีไฟล์ต้องระบุเหตุผลและหลักฐานทดแทน
4. ส่งตรวจ ผู้ตรวจต้องตรงชื่อและบทบาทที่ตั้ง ส่งกลับพร้อมเหตุผลหรือยืนยันได้ ร่าง/รอตรวจ/ส่งกลับยังไม่รวมยอด
5. เตือนสงสัยซ้ำจากไฟล์เดียวกัน ร้าน+เลขบิล หรือร้าน+วัน+ยอด+สกุลเงิน ต้องให้คนทวนและรับรองพร้อมคำอธิบาย ไม่ตัดสินว่าซ้ำอัตโนมัติ
6. เตือนเมื่อไม่มีหลักฐาน ใบซื้อยังไม่ปิดรับ รับบางส่วน หรือยอด/สกุลเงินต่างจากใบซื้อ ให้คนอธิบายก่อนผ่าน
7. รวมเฉพาะยืนยันแล้ว แยกสกุลเงินและแหล่งเงิน ไม่คิดอัตราแลกเปลี่ยน ยืนยันแล้วแก้ยอดไม่ได้ เจ้าของยกเลิกพร้อมประวัติและสร้างรายการแก้ใหม่ได้
8. ไฟล์หลักฐานรวมใน JSON สำรอง/นำเข้าและดาวน์โหลดคืนได้ อย่าล้างเบราว์เซอร์ก่อนสำรอง

**ขอบเขต F07:** แนบหลักฐานและกรอก/แก้ร่างทำได้แล้ว แต่ AI/OCR ยังไม่เชื่อมต่อ ไม่แสดงผลอ่านจำลองหรือเดาตัวเลข ต้องกรอกและตรวจเอง ส่วนนี้ยังไม่ถือว่าฟีเจอร์ AI เสร็จ
**ขอบเขต F08:** ขั้นส่งกลับ/ตรวจ/ยืนยันและรวมยอดพร้อมทดลอง ผู้ตรวจจริงและเกณฑ์กรณีไม่มีบิลยังต้องตกลงก่อนใช้จริง
เงินสำรองส่วนตัวเป็นแหล่งเงินที่จ่าย ไม่ใช่ยอดค้างคืน ไม่มีการบันทึกคืนเงิน/โอนเงินอัตโนมัติ บทบาทจำลองไม่ใช่ความปลอดภัยจริง พนักงานยังไม่เปิดข้อมูลค่าใช้จ่าย

ข้อมูล schema 6 ใช้ key เดิม พร้อมสำรองก่อน migration ที่ daldal-operations-data-before-v6. receipts และ purchaseOrders เดิมคงไว้. เพิ่ม expenses / expenseReviewer, เก็บยอดเงินเป็นจำนวนเต็มหน่วยย่อย, audit ก่อน/หลังแก้ร่าง. พื้นที่เต็มปฏิเสธการบันทึกและรักษาชุดเดิม.

## รอบที่ 7 — Dashboard และรายงาน (v0.7.0, 29 ตุลาคม 2026)

- เปิดเมนู Dashboard / รายงาน ดูสต็อกเข้าเกณฑ์เตือน วัตถุดิบที่ยังไม่นับ และที่ยังไม่รับรองเคลื่อนไหวครบ พร้อมงานค้างจากนับ/เสนอซื้อ/จัดซื้อ/รับ/บิล
- สต็อกและงานค้างเป็นสถานะปัจจุบันทั้งหมด ไม่เปลี่ยนตามตัวกรองวัน ยอดอ้างอิงยังยึดกฎเดิม: ใช้ยอดนับจนกว่ารับรองเคลื่อนไหวครบ
- เลือกช่วงวันที่ รวมวันแรกและวันสุดท้ายตามเวลาไทย; เดือนนี้/ทั้งหมด; ช่วงผิดแสดงข้อผิดพลาด
- ค่าใช้จ่ายกรองวันที่บิลและสถานะยืนยันปัจจุบัน แยกสกุลเงิน/เงินร้าน/สำรองส่วนตัว/หมวด ยกเลิกภายหลังทำให้รายงานช่วงเดิมเปลี่ยน
- จัดซื้อกรองวันที่บันทึกซื้อ แสดงยอดเต็มตามใบและสถานะรับสะสมปัจจุบัน ไม่หักคืนเงิน/ส่วนที่ไม่รับ และไม่บวกยอดนี้กับค่าใช้จ่าย
- เคลื่อนไหวกรองเวลาบันทึก แยกวัตถุดิบและหน่วย รวมรายการกลับยอด แสดงสุทธิเป็นการเปลี่ยนแปลงในช่วง ไม่ใช่คงเหลือหรือยอดใช้จากการขาย
- ตรวจรับกรองเวลายืนยัน เฉพาะใบที่ยัง confirmed ไม่รวม void แยกจำนวนรับ/ไม่รับ
- เปิดใบซื้อ ใบรับ และค่าใช้จ่ายต้นทางจากรายงานได้ตรงรายการ; งานนับและเสนอซื้อเปิดหน้ากลุ่มงาน
- ส่งออก CSV 5 ประเภท: สต็อกปัจจุบัน เคลื่อนไหว ตรวจรับ จัดซื้อ ค่าใช้จ่าย พร้อมขอบเขตวันและเวลาสร้าง ใช้ UTF-8 BOM และป้องกันข้อความผู้ใช้ถูกตีความเป็นสูตร
- staff เห็นเฉพาะรายงานสต็อก/รับและงานที่อนุญาต; owner/manager เห็นรายงานการเงินตามบทบาทจำลอง

รายงานไม่เปลี่ยนข้อมูล ไม่เพิ่ม schema ใช้ schema 6 เดิม ไม่มีข้อมูลยอดขาย/กำไร ไม่ใช่งบปิดย้อนหลัง ข้อมูลเบราว์เซอร์นี้เท่านั้น

สถานะหลังครบหน้าจอ 7 รอบ: F01–F06, F08, F09 พร้อมทดลอง; F07 แนบหลักฐาน/ร่างทำได้ แต่ AI/OCR ยังไม่เชื่อม; F10 บทบาทจำลอง ยังไม่มีบัญชี/สิทธิ์จริง ฐานข้อมูลส่วนกลางและไฟล์หลักฐานส่วนกลางยังไม่ทำ
