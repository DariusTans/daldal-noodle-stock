# ส่งต่องาน Daldal

## ข้อตกลง

## สถานะ v0.8.1 / รอบ 8
ทะเบียนวัตถุดิบ หน่วยนับ บทบาทจำลอง นับ/ตรวจยืนยัน เคลื่อนไหว/ตรวจความครบ จุดเตือน เสนอซื้อ และจัดซื้อ/พิจารณาพร้อมใช้งานในต้นแบบ source คือ index.html และ assets; dist เป็นสำเนาเผยแพร่

## ข้อจำกัด
ยังไม่มีฐานข้อมูลส่วนกลาง/บัญชีผู้ใช้จริง ทุกคนสลับบทบาทจำลองได้ บทบาทกลับเป็นเจ้าของเมื่อ reload เป็นพฤติกรรมต้นแบบเดิม ผู้ตรวจที่อนุญาตคือ owner/manager เป็นข้อเสนอ ต้องยืนยันการมอบหมายจริง ยอดนับก่อน ≠ ยอดคาดหมายจากเคลื่อนไหว ไม่มีการหักสต็อกจากยอดขาย

## กฎสำคัญรอบ 3
movements อ้างอิง confirmed count roundId และหน่วยเดิม กลับรายการด้วยรายการหักล้างใหม่ ไม่แก้ของเก่า ห้ามยอดคำนวณติดลบ ไม่มีการลงย้อนหลัง หรือรับของที่นับรวมแล้วซ้ำ
stockChecks รับรองรายการทั้งหมด ณ เวลาตรวจ ผูก roundId + ลำดับ movement IDs; มีรายการใหม่จะไม่ถือว่าตรวจครบอีก หากยังไม่ครบ referenceQty = latest confirmed count ส่วน ledger แสดงแยกเป็นยอดคำนวณที่ยังไม่ใช้เตือน
เปิดรอบนับพัก movements/checks/proposals จนจบรอบ snapshot expectedQty เฉพาะที่ตรวจครบ ยืนยันรอบใหม่ใช้ฐานใหม่ไม่รวม movements ของฐานเก่า
นับและ confirm ใน counts-core รองรับ optional expectedQty โดยเทียบยอดนั้นแทน previousQty เมื่อมี; ประวัติเดิมยังเทียบแบบเดิม
stockPolicies เก็บ minimum/target ต่อ ingredient ไม่มีค่าเริ่มต้น เตือน referenceQty <= minimum, suggest target - referenceQty
purchaseRequests: draft → ready หรือ cancelled; ready = ตรวจจำนวนแล้วรอจัดซื้อ ไม่ใช่อนุมัติหรือซื้อแล้ว ป้องกันซ้ำ ingredient ที่ยังไม่ cancelled fingerprint ใช้ count/movement/check/policy; ถ้าเปลี่ยนปฏิเสธยืนยันจน refresh ร่าง (หรือ cancel ถ้าไม่เข้าเกณฑ์)

## กฎและผลตรวจรอบ 4
purchaseOrders อ้างอิง purchaseRequests.status=ready ใช้หนึ่งรายการต่อหนึ่งใบ กันซ้ำใบ active รวม ordered; ถ้ามีใบ active ห้าม cancel request ต้นทาง
สถานะ draft/returned → pending → approved หรือ cleared → ordered; return/reject มีเหตุผล; cancelled/rejected ปิดใบ สร้างใบใหม่จาก source ได้; ordered ล็อกไว้รอตรวจรับ
purchasePolicy เริ่ม null ต้อง owner ตั้ง currency / all หรือ above / threshold ต่อใบ / approver+role / note พร้อมรับรองทดลอง ก่อน submit ไม่มีค่า 5,000 สมมติ ใช้ > แบบ strict; below/equal ต้องคนรับรอง clear
ราคาทั้งหมดเก็บหน่วยย่อยเงินเป็น integer 1/100; qty ทศนิยม 3 หลัก; ชุดซื้อ=ceil(qty/packQty) และเก็บ orderedQty ที่ปัดตามบรรจุจริง ตัวเลขเงินกรอกได้ 2 ทศนิยม
ฟอร์มขนาดซื้อเป็นหน่วยนับเดิม ไม่แปลงสกุลเงิน ไม่รวมข้ามใบ ไม่ fetch ราคาสดหรือออกคำสั่งซื้อ
ก่อน submit/approve/order ตรวจ sourceFingerprint; ถ้าเปลี่ยนใช้ reviewOrderSource ใน draft/returned เพื่อบันทึก qty+reason+ผู้ทบทวน และเลือก offer ใหม่
ราคา/รายละเอียดเปลี่ยนหลัง pending/approval ต้อง reviseOrder ล้าง decision กลับ draft โดยเก็บการตัดสินเก่าใน audit เกณฑ์ policy ID เปลี่ยนกัน approve/order จนส่งใหม่
approved/cleared มี decision snapshot รวม qty/offer/total/sourceFingerprint และ policySnapshot; ordered.purchase snapshot มี reference/person/at/offer/qty/orderedQty/packCount/total/receivedQty=0
การ markOrdered ไม่เพิ่ม movements ไม่เพิ่มยอดสต็อก ไม่ลงค่าใช้จ่าย ไม่มีการซื้อหรือจ่ายเงินจริงจากระบบ
staff ซ่อนราคา/หน้าจัดซื้อทั้ง UI และ core mutations แต่ยังเป็น localStorage และบทบาทจำลองไม่ใช่ security

ผ่าน tests/buy.test.cjs: migration 3→4 คง source, กันซ้ำ, rounding บรรจุ/เงิน, สกุลเงิน, policy gate, threshold เท่ากัน/เกิน, ชื่อ/role reviewer, return/reject, ล้าง approval เมื่อแก้, stale policy/source, ordered snapshot ไม่เพิ่มสต็อก, validate ไฟล์ผิด
ผ่าน tests/buy-browser.cjs: migrate พร้อม backup v3, staff มองไม่เห็นราคา, create/quote/select, กั้นไม่มี policy, return/approve/revise/reapprove/order, reload/JSON import, cross-tab conflict และ desktop/mobile ไม่มี page error
Regression core/counts/stock logic และ browser รอบ 1–3 ผ่านบน source รอบ 4 โดย browser assertions เปลี่ยนเป็น schema 4

## รอบที่ 5 — ตรวจรับสินค้า (v0.5.0)

- เปิดเมนูตรวจรับจากใบซื้อเดิม จำนวนคาดรับใช้จำนวนสั่งจริงหลังปัดบรรจุ
- พนักงานร่างผลตรวจ จำนวนผ่านตรวจ/ไม่รับ เลขส่งของ ผู้ตรวจ และหมายเหตุ โดยไม่แสดงราคา
- ผู้จัดการหรือเจ้าของรับรองผลตรวจและยืนยันว่ายังไม่รวมของนี้ในยอดนับก่อนยืนยันลงสต็อกครั้งเดียว
- รองรับรับบางส่วน ของเสียหาย/ผิดรายการ ติดตามผล และส่งทดแทนด้วยใบรับใหม่
- ยกเลิกร่างหรือกลับยอดใบรับพร้อมประวัติได้ก่อนปิดรับ การกลับยอดต้องยังอยู่ในฐานนับเดิมและยอดคงเหลือพอ
- ปิดรับครบหรือปิดบางส่วนพร้อมเหตุผลและรับรองไม่รับส่วนที่เหลือ ต้องเคลียร์ร่างและปัญหาค้างก่อน เมื่อปิดแล้วรายการเสนอซื้อเสร็จสิ้น เปิดเสนอรอบใหม่ได้
- ปิดรับไม่คืนเงินหรือรับรองค่าใช้จ่าย การยืนยันรับไม่เท่ากับรับรองว่ารายการเคลื่อนไหวทั้งหมดครบ
- เก็บ storage key เดิม อัปเกรด schema 1–4 เป็น 5 พร้อมสำรองต้นฉบับ before-v5; ไม่ seed ทับข้อมูลเดิม

ข้อจำกัด: ยังคงเป็นต้นแบบเก็บข้อมูลในเบราว์เซอร์ บทบาทจำลอง ไม่มีบัญชีจริงหรือฐานข้อมูลส่วนกลาง ไม่รับเกินใบซื้อ ไม่เปิดแก้ใบที่ปิดรับแล้ว หากยอดรวมอยู่ในการนับไปแล้วห้ามรับซ้ำ

โครงสร้างเพิ่ม receive-core.js / receive-ui.js / receive.css; receipts เชื่อม movementId / receiptId / purchaseOrderId; purchase.receivedQty รวมเฉพาะ confirmed. Order คง ordered และมี receiving.status open/closed; request เปลี่ยน completed เมื่อปิดรับ จึงปลดการกันเสนอซื้อซ้ำ. Core รอบ 3/4 รองรับ completed เพื่อรักษาการตรวจข้อมูลข้ามรุ่น.
ตรวจรอบ 5: logic migration/partial/reject/role/exactly-once/reversal/duplicate/close/stale count/import ผ่าน; browser ตรวจ workflow รับถึงปิด รวม backup/import, cross-tab, mobile. Regression รอบ 1–4 ผ่าน. ไม่เพิ่มงานรอบ 6 ในรุ่นนี้.

## รอบที่ 6 — บิลและค่าใช้จ่าย (v0.6.0, 29 ตุลาคม 2026)

1. เจ้าของตั้งชื่อและบทบาทผู้ตรวจทดลองก่อนส่งตรวจ ไม่สมมติผู้ตรวจให้ร้าน
2. ผู้จัดการ/เจ้าของสร้างร่าง: ร้านค้า วันที่ เลขบิล ยอดรวม สกุลเงิน หมวด เงินร้าน/สำรองส่วนตัว ชื่อผู้จ่าย และรายละเอียด เชื่อมใบซื้อเดิมได้โดยไม่เพิ่มสต็อก
3. แนบหลักฐาน PNG/JPEG/WebP/PDF หนึ่งไฟล์ต่อรายการ ไม่เกิน 350 KB รวมไม่เกิน 1.4 MB เพื่อใช้กับพื้นที่เบราว์เซอร์ หากไม่มีไฟล์ต้องระบุเหตุผลและหลักฐานทดแทน
4. ส่งตรวจ ผู้ตรวจต้องตรงชื่อและบทบาทที่ตั้ง ส่งกลับพร้อมเหตุผลหรือยืนยันได้ ร่าง/รอตรวจ/ส่งกลับยังไม่รวมยอด
5. เตือนสงสัยซ้ำจากไฟล์เดียวกัน ร้าน+เลขบิล หรือร้าน+วัน+ยอด+สกุลเงิน ต้องให้คนทวนและรับรองพร้อมคำอธิบาย ไม่ตัดสินว่าซ้ำอัตโนมัติ
6. เตือนเมื่อไม่มีหลักฐาน ใบซื้อยังไม่ปิดรับ รับบางส่วน หรือยอด/สกุลเงินต่างจากใบซื้อ ให้คนอธิบายก่อนผ่าน
7. รวมเฉพาะยืนยันแล้ว แยกสกุลเงินและแหล่งเงิน ไม่คิดอัตราแลกเปลี่ยน ยืนยันแล้วแก้ยอดไม่ได้ เจ้าของยกเลิกพร้อมประวัติและสร้างรายการแก้ใหม่ได้
8. ไฟล์หลักฐานรวมใน JSON สำรอง/นำเข้าและดาวน์โหลดคืนได้ อย่าล้างเบราว์เซอร์ก่อนสำรอง

**ขอบเขต F07:** แนบหลักฐานและกรอก/แก้ร่างทำได้แล้ว แต่ AI/OCR ยังไม่เชื่อมต่อ ไม่แสดงผลอ่านจำลองหรือเดาตัวเลข ต้องกรอกและตรวจเอง ส่วนนี้ยังไม่ถือว่าฟีเจอร์ AI เสร็จ
**ขอบเขต F08:** ขั้นส่งกลับ/ตรวจ/ยืนยันและรวมยอดพร้อมทดลอง ผู้ตรวจจริงและเกณฑ์กรณีไม่มีบิลยังต้องตกลงก่อนใช้จริง
เงินสำรองส่วนตัวเป็นแหล่งเงินที่จ่าย ไม่ใช่ยอดค้างคืน ไม่มีการบันทึกคืนเงิน/โอนเงินอัตโนมัติ บทบาทจำลองไม่ใช่ความปลอดภัยจริง พนักงานยังไม่เปิดข้อมูลค่าใช้จ่าย

## รอบที่ 7 — Dashboard และรายงาน (v0.7.0, 29 ตุลาคม 2026)

- เปิดเมนู Dashboard / รายงาน ดูสต็อกเข้าเกณฑ์เตือน วัตถุดิบที่ยังไม่นับ และที่ยังไม่รับรองเคลื่อนไหวครบ พร้อมงานค้างจากนับ/เสนอซื้อ/จัดซื้อ/รับ/บิล
- สต็อกและงานค้างเป็นสถานะปัจจุบันทั้งหมด ไม่เปลี่ยนตามตัวกรองวัน ยอดอ้างอิงยังยึดกฎเดิม: ใช้ยอดนับจนกว่ารับรองเคลื่อนไหวครบ
- เลือกช่วงวันที่ รวมวันแรกและวันสุดท้ายตามเวลาไทย; เดือนนี้/ทั้งหมด; ช่วงผิดแสดงข้อผิดพลาด
- ค่าใช้จ่ายกรองวันที่บิลและสถานะยืนยันปัจจุบัน แยกสกุลเงิน/เงินร้าน/สำรองส่วนตัว/หมวด ยกเลิกภายหลังทำให้รายงานช่วงเดิมเปลี่ยน
- จัดซื้อกรองวันที่บันทึกซื้อ แสดงยอดเต็มตามใบและสถานะรับสะสมปัจจุบัน ไม่หักคืนเงิน/ส่วนที่ไม่รับ และไม่บวกยอดนี้กับค่าใช้จ่าย
- เคลื่อนไหวกรองเวลาบันทึก แยกวัตถุดิบและหน่วย รวมรายการกลับยอด แสดงสุทธิเป็นการเปลี่ยนแปลงในช่วง ไม่ใช่คงเหลือหรือยอดใช้จากการขาย
- ตรวจรับกรองเวลายืนยัน เฉพาะใบที่ยัง confirmed ไม่รวม void แยกจำนวนรับ/ไม่รับ
- เปิดใบซื้อ ใบรับ และค่าใช้จ่ายต้นทางจากรายงานได้ตรงรายการ; งานนับและเสนอซื้อเปิดหน้ากลุ่มงาน
- ส่งออก CSV 5 ประเภท: สต็อกปัจจุบัน เคลื่อนไหว ตรวจรับ จัดซื้อ ค่าใช้จ่าย พร้อมขอบเขตวันและเวลาสร้าง ใช้ UTF-8 BOM และป้องกันข้อความผู้ใช้ถูกตีความเป็นสูตร
- staff เห็นเฉพาะรายงานสต็อก/รับและงานที่อนุญาต; owner/manager เห็นรายงานการเงินตามบทบาทจำลอง

รายงานไม่เปลี่ยนข้อมูล ไม่เพิ่ม schema ใช้ schema 6 เดิม ไม่มีข้อมูลยอดขาย/กำไร ไม่ใช่งบปิดย้อนหลัง ข้อมูลเบราว์เซอร์นี้เท่านั้น

## ข้อมูลตัวอย่าง

assets/demo-data.js สร้างข้อมูลโดยใช้กฎ core เดิมและตรวจ validate; demo-mode.js เลือกพื้นที่ก่อน app.js เริ่ม ค่าเริ่มต้นเป็น demo key daldal-operations-demo-v1 (backup key แยก) ส่วน ?data=workspace ใช้ daldal-operations-data เดิม ไม่เปลี่ยน schema และไม่รวมข้อมูลระหว่างสองพื้นที่ ตัวอย่างเก็บต่อหลัง reload ไม่ reseed เมื่อมีข้อมูลแล้ว
